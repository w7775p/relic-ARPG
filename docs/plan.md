# 3D 刷宝游戏工程规范与阶段计划

版本：v0.2。日期：2026-09-09。性质：完整阶段规划；M0 已开始实现，当前交付与验证以 README、tasks.md 和 validation.md 为准。本文后续阶段及示例不代表已实现。工程内部代号暂用 `relic_arpg`，正式游戏名称待定。

本文将已讨论的功能落实为目录、职责、命名、资产交付、中文注释、Godot 实现与阶段验收。当前方向为单机、3D 固定俯视镜头、即时动作刷宝，主要体验是亲手击杀怪群、获得随机装备，并在 BD（技能与装备构筑）成型后高速清图。世界观与正式美术方向待确认。

## 01 工程基准

| 项目 | 本版规划 |
| --- | --- |
| 引擎与语言 | Godot 4.7.2 标准版，GDScript；编辑器与导出模板使用相同版本。官方 Windows 下载页当前列出 4.7.2 [1] |
| 首发验证平台 | 暂定 Windows x86_64、键鼠；这是本项目建议，不沿用其他项目的移动端要求 |
| 渲染 | M0 使用兼容渲染器；M1 在目标电脑实测后评估 Forward+（前向增强渲染），记录显卡和驱动。渲染器选择依赖硬件及所需效果 [2] |
| 摄像机 | 固定方向俯视，M0 先用正交投影；将镜头角度、视野大小和跟随速度作为配置 |
| 美术方向 | 风格化低多边形，统一比例和材质，模块化地牢；先用可复用资产验证生产流程 |
| 第一套构筑 | 雷霆旋风：持续旋风斩、暴击连锁闪电、感电死亡爆炸、能量回复 |
| 核心循环 | 出发 → 实时清怪 → 地面掉落 → 拾取换装 → 清怪效率变化 → 整备 → 再次出发 |
| MVP 定义 | 一趟可以完整游玩的刷宝流程，包含随机掉落、装备生效及存档恢复 |
| Demo 定义 | 在 MVP 上补齐构筑选择、重复探索、内容表现和交付质量，可交给新玩家独立体验 |
| 参数状态 | 本文中的数量、时长、面数和性能数值都是初始目标，按试玩或测量调整 |

开工时在 `docs/engineering.md` 记录引擎完整版本、渲染器、导出模板版本、插件版本和目标电脑。引擎升级放在单独分支完成导入、存档和导出验证后合并。

## 03 代码与内容命名

以下规则与 Godot 的 GDScript 风格保持一致 [3][4]。代码标识符使用英文，功能说明、备注及玩家可见文本使用中文。

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 文件、目录 | 小写下划线；名称描述职责 | `loot_generator.gd`、`whirlwind.tscn` |
| 类、节点 | 首字母大写的驼峰式 | `ItemInstance`、`HealthComponent`、`VisualRoot` |
| 函数 | 小写下划线，动词开头 | `generate_item()`、`apply_damage()` |
| 变量、参数 | 小写下划线，注明含义 | `item_level`、`source_actor` |
| 布尔值 | 使用 `is_`、`has_`、`can_` | `is_dead`、`can_cast` |
| 内部成员 | 前置下划线 | `_hit_targets` |
| 常量、枚举成员 | 全大写下划线 | `MAX_SKILL_SLOTS`、`DamageType.LIGHTNING` |
| 信号 | 描述已发生的事件 | `health_changed`、`actor_died`、`equipment_changed` |
| 信号回调 | `_on_来源_事件` | `_on_health_component_actor_died()` |
| 输入动作 | 小写下划线，使用含义 | `move_left`、`primary_attack`、`channel_skill`、`dodge` |
| 分组 | 小写复数或职责名 | `enemies`、`loot_pickups` |
| 内容 ID | 类型前缀与语义，创建后保持稳定 | `skill_whirlwind`、`affix_critical_chance`、`enemy_skeleton_melee` |
| 文件版本 | 交给 Git；导出包带版本 | `relic_arpg_0.2.0_mvp_windows.zip` |
| 量纲 | 数字名称带单位或语义后缀 | `duration_sec`、`radius_m`、`move_speed_mps`、`critical_chance` |

① 编码使用 UTF-8，无字节序标记；换行使用 LF；GDScript 使用制表符缩进，单行尽量控制在 100 字符以内。文件末尾保留一个换行。

② 新增函数的参数与返回值声明类型。编辑器可调参数使用 `@export`；跨系统的核心数据使用明确的自定义类。字典主要用于序列化与边界转换。

③ 概率统一为 0～1；时间以秒、距离以米、速度以米每秒表示。显示百分数时再乘 100。将冷却、范围和权重写进配置，避免同一个数值散落在多个脚本。

④ `definition` 表示静态定义，`instance` 表示已生成的独立对象，`state` 表示当前运行状态，`view` 表示显示。Godot 的资源 UID 与游戏物品实例编号分别使用，存档中的物品身份由独立编号维护。

⑤ 子节点引用优先在场景中连接或通过导出引用指定；需要直接路径时使用稳定的局部路径。跨系统由拥有者注入依赖。分组用于确有全局集合需求的操作，热路径中的目标查找通过物理查询或局部目标集合完成。

⑥ 静态场景连接在编辑器中可见；动态生成对象在创建时连接一次信号。游戏规则通过事件通知界面，界面按钮提交操作请求。自动加载服务使用 `SceneRouter` 等名称，对应脚本使用 `scene_router.gd`，避免同名 `class_name` 冲突。

## 04 中文注释与备注格式

所有新增类、函数和玩法功能都配简明中文说明，包括内部函数和引擎回调。函数注释写用途；参数单位、返回值或副作用容易误解时再补充。普通注释使用 `# `，供编辑器文档使用的注释使用 `## `，Godot 支持脚本及成员文档注释 [5]。

下面仅示范格式，尚未运行。实际角色需要在创建或读档时初始化当前能量。

```gdscript
class_name EnergyComponent
extends Node
## 管理角色当前能量，供技能扣除消耗与触发效果回复。

signal energy_changed(current: float)

var current_energy: float = 100.0


## 尝试消耗能量。amount 为非负能量值；返回是否成功，成功后通知界面。
func try_spend_energy(amount: float) -> bool:
	if amount < 0.0 or current_energy < amount:
		return false

	current_energy -= amount
	energy_changed.emit(current_energy)
	return true
```

| 场景 | 中文格式 |
| --- | --- |
| 类说明 | `## 负责装备实例生成，根据底材、品质和词条池创建独立物品。` |
| 参数说明 | `## 每次连锁的最大距离，单位：米。` |
| 规则原因 | `# 同一段攻击按角色编号去重，防止多个受击形状重复扣血。` |
| 尚待工作 | `# 待办[M2-LOOT-03]：补齐词条池为空时的降级规则；完成条件：生成结果符合品质规则。` |
| 临时问题 | `# 临时[M1-VFX-02]：当前闪电使用线段表现，正式效果在 D2 替换。` |
| 已知缺陷 | `# 已知问题[M1-AI-04]：狭窄门口会拥堵；复现步骤见 known_trap.md 对应编号。` |
| 待验证 | `# 待验证[D3-PERF-01]：目标电脑上 200 个活动敌人的帧时间。` |

任务备注统一使用：`编号｜所属阶段｜系统｜具体工作｜前置依赖｜交付文件或场景｜验收步骤与预期｜状态｜备注`。例如：`M2-LOOT-01｜M2｜掉落｜精英掉落随机装备｜装备实例与死亡事件｜精英掉落表及生成器｜击杀后出现物品，拾取后词条数值保持一致｜未开始｜概率以资源配置为准`。

资产交付备注统一使用：`资产ID｜名称｜来源或作者｜源文件｜引擎文件｜尺寸或规格｜绑定与动画｜材质｜许可证｜状态｜导入验收结果`。

工作日志统一使用：`日期｜任务编号｜实际改动｜验证方式及结果｜遗留问题｜下一项工作`。开工前阅读 `known_trap.md`，工作后只追加本次确实遇到的新问题；理论风险写进规划或测试用例。

## 05 资产生产与交付规范

### 05.1 通用规则

资产遵循“源工程 → 引擎导出文件 → Godot 包装场景”的交付流程。源工程放 `source_art/`，引擎文件放所属功能目录，包装场景添加碰撞、挂点及脚本。3D 交换格式统一 glTF 2.0 的 `.glb`；Godot 官方推荐 glTF，直接导入 `.blend` 则依赖本机安装 Blender [6]。第三方资源优先选择已具备所需骨骼、动作和许可证的包，使用前做一次真实导入验收。

资产文件采用 `主体_用途_变体` 命名，例如 `skeleton_melee.glb`、`skeleton_albedo.png`、`sword_hit_01.wav`。变体编号表示不同内容；版本历史由 Git 保留。直接复用的第三方资源尽量保持原文件名，在资产台账中建立映射。

| 类别 | 初始交付规格 | 验收重点 |
| --- | --- | --- |
| 比例与坐标 | 1 引擎单位按 1 米使用；Y 轴向上；标准人形约 1.8 米；玩法前向统一为 -Z | 导入后的比例、脚底位置、握持位置正确；外部素材的朝向修正在视觉包装节点 |
| 变换与原点 | 模型应用缩放，运行场景根缩放为 1；角色原点在两脚之间地面，门和可旋转物件在铰接点 | 换模型后碰撞、技能范围与导航尺寸保持一致 |
| 角色网格 | 玩家初始预算 5,000～10,000 三角面；普通怪 1,500～4,000；首领 8,000～15,000 | 三角面数、材质槽和骨骼动画的实际开销一起测量 |
| 骨骼 | 同类人形优先共用骨架；单顶点最多 4 个骨骼权重作为资产约定；预留武器与特效挂点 | 动画能复用，骨骼命名一致，关节变形及武器挂点正确 |
| 动画 | 原地动画；源文件采样暂用 30 帧每秒；`idle`、`run`、`attack_01`、`whirlwind_loop`、`dodge`、`hit`、`die` | 走跑循环衔接，动作与攻击窗口相符；速度缩放后仍能辨识动作 |
| 地图模块 | 地面按 4×4 米模块制作，使用 1 米吸附网格；门口宽度暂为 4 米；边缘与入口对齐 | 可以无缝拼接，角色能通过接缝，怪群通过门口时可接受 |
| 碰撞 | 角色使用胶囊体；墙体使用盒体或简单凸体；复杂静态碰撞仅用于确有必要的地形 | 碰撞与画面一致，角色不会卡在装饰物细节上 |
| 材质与贴图 | 普通怪优先 1 个材质槽、512 或 1024 贴图；玩家与首领按需使用 1024 或 2048；公共调色板及材质复用 | 批量怪群材质一致，正常导入纹理；透明材质有明确用途 |
| 贴图类型 | `albedo`（基础色）、`normal`（法线）、`orm`（遮蔽/粗糙度/金属度合图）；ORM 按 R/G/B 顺序约定 | 数据贴图按线性数据处理；3D 缩小时启用合适的多级渐远纹理 |
| 装备图标 | 256×256 透明 PNG，游戏中以 64～96 像素展示；主体方向、留白和光照统一 | 小尺寸仍能分辨装备类型；品质边框由界面统一绘制 |
| 界面 | 设计基准 1920×1080，验收到 1280×720；正文初始 20 像素；使用容器和主题 | 长中文词条、窗口缩放、背包满格仍能正常排版 |
| 字体 | 具有所需中文字符的 `.ttf` 或 `.otf`，随项目保留许可证 | 中文、数字、符号缺字检查，文本换行正常 |
| 音效 | 短音效源文件使用无损 WAV；空间音效通常单声道；相似命中准备 3～5 个变体 | 多次播放有差异，能分清玩家受击、怪物死亡与稀有掉落 |
| 音乐与环境声 | 长音频可导出 Ogg Vorbis，循环点在源工程标记；制作采样率暂统一 48 kHz | 循环无明显接缝，整体混音保留余量；格式与加载方式按实际长度选择 [7] |
| 特效 | 明确持续时间、作用范围、颜色、朝向、挂点及同屏预算；释放后自行回收 | 显示范围贴近判定范围，危险区域和稀有掉落仍可辨认 |

### 05.2 导入与复用规则

① 导入模型后创建 `player_visual.tscn` 等包装场景，由玩法场景实例化；材质替换、挂点和脚本集中在包装层，重新导出模型后检查覆盖结果。

② 移动和闪避由控制器驱动，动画跟随实际速度。攻击发生时间由技能运行状态提供，动画方法轨道可提交事件，最终命中与伤害进入物理步处理。连续旋风只旋转视觉节点，角色碰撞体与镜头保持稳定。

③ 用同一个资产检查场景展示人形比例、武器挂点、基础动作、命中效果和一段地形。通过检查后再批量制作同类资产。

④ 每项外部资产保存来源、作者、版本和许可证。发行包中的署名根据实际资产许可证填写；进入 Demo 内容验收时清理仍需替换的占位物。

## 06 Godot 场景与运行职责

### 06.1 全局服务与地图内服务

自动加载仅保留跨场景持续存在的服务：`SceneRouter`（场景切换）、`SettingsManager`（设置）、`AudioManager`（混音与全局音频）、`SaveManager`（保存与恢复）。M0 先检查已有底座，具备相同职责的服务直接适配。当前规划并未确认已有仓库或代码可以直接复用。

### 06.3 输入与碰撞层

初始键位：WASD 移动，鼠标左键普攻，右键持续旋风，空格闪避，Q 药剂，E 交互，I 背包，Esc 暂停。所有键位先映射到语义动作，D3 提供玩家重绑定。旋风输入松开、能量不足或角色死亡时停止；打开菜单时清除持续施法输入。

| 3D 物理层 | 名称 | 放置对象 |
| --- | --- | --- |
| 1 | `world` | 地面、墙体、不可穿过的地形 |
| 2 | `player_body` | 玩家移动碰撞体 |
| 3 | `enemy_body` | 敌人移动碰撞体 |
| 4 | `player_hurtbox` | 玩家受击区域 |
| 5 | `enemy_hurtbox` | 敌人受击区域 |
| 6 | `loot` | 地面战利品拾取区域 |
| 7 | `interactable` | 门、宝箱、出口等交互区域 |
| 8 | `aim_ground` | 用于鼠标投射的地表；地面可同时位于第 1 和第 8 层 |

玩家攻击查询第 5 层，敌人攻击查询第 4 层；投射物同时检查世界阻挡和目标受击层；瞄准查询第 8 层。角色初始仅与世界进行硬碰撞，怪群用导航与局部分离处理间距，防止堆叠挤压持续影响割草移动。需要强化身体阻挡的精英在对应阶段单独设计。

### 06.4 物理与动画更新

角色的水平 `velocity` 使用米每秒，调用 `move_and_slide()` 时引擎自行使用物理步长；加速度、重力和持续消耗按 `delta` 积分 [8]。物理查询安排在物理回调内，输入阶段只记录意图 [9]。攻击以技能间隔触发，避免把“每帧执行一次”误当成固定攻击频率。

`AnimationTree` 使用状态机与混合衔接站立、移动和攻击，视觉旋转和动作速度来自角色实际状态 [12]。持续伤害、连锁次数和冷却都以游戏时间为准，暂停时同步暂停。命中反馈优先使用模型动作、武器轨迹、声音和轻微镜头反馈；连续割草中的每次命中都暂停全场会破坏速度感，常规命中采用局部反馈。

## 07 装备配置与战斗事件

### 07.1 数据定义与运行实例

静态配置由自定义 `Resource` 保存为 `.tres`，通过检查器维护；Godot 原生支持此类资源的编辑与序列化 [11]。同一路径资源可能被共享加载，装备浮动数值、角色生命和状态叠层使用各自的运行实例。所有基础词条在一张定义表中维护，各物品通过 ID 引用。

| 数据类型 | 至少包含的字段 |
| --- | --- |
| `ItemBaseDefinition` 装备底材 | `id`、中文名称、部位、基础属性、物品标签、最低等级、图标、地面模型 |
| `AffixDefinition` 随机词条 | `id`、中文说明模板、适用标签、互斥组、档位、数值上下界、抽取权重、属性或效果引用 |
| `UniqueItemDefinition` 独特装备 | `id`、底材ID、固定属性、固定效果、可浮动参数、来源标签 |
| `SkillDefinition` 技能 | `id`、中文名称、技能标签、消耗、间隔、范围、系数、施法方式、表现引用 |
| `EffectDefinition` 效果 | `id`、事件、来源要求、条件、效果参数、目标规则、叠层与持续规则 |
| `LootTable` 掉落表 | `id`、抽取次数、候选池、权重、品质分布、保证奖励规则 |
| `EncounterDefinition` 遭遇 | `id`、敌人组合、数量、出生间隔、活动距离、奖励引用 |
| `RegionDefinition` 区域 | `id`、地图或房间池、遭遇池、难度、掉落等级和专属物品权重 |
| `ItemInstance` 装备实例 | 实例编号、底材ID、独特装备ID、等级、品质、已抽出的词条与数值、重铸位置、锁定状态 |

`catalog.tres` 显式引用正式内容。启动时按 ID 建立字典索引并检查重复 ID 与缺失引用；导出时这些依赖随资源打包。MVP 直接维护 `.tres`；后续若改用表格批量生产，则指定表格为唯一编辑源并生成 `.tres`，同时停止手动修改生成结果。

### 07.2 掉落生成顺序

来源确定掉落表 → 抽取类别与底材 → 确定物品等级和品质 → 筛选满足标签与档位的词条 → 按权重抽取且移除互斥候选 → 抽取各词条数值 → 创建独立实例 → 生成地面物品。每次抽取均使用配置中的实际权重。

生成流程在本地执行，配置随单机游戏打包。加权候选选择优先使用 `RandomNumberGenerator.rand_weighted()`，选中后更新候选与权重；数值范围使用相应整数或浮点随机方法 [15]。

魔法装备初设 1～2 条随机词条，稀有装备初设 3～4 条，独特装备使用专属定义。正式品质规则要求足够合法候选；配置检查发现候选不足时要求修正。运行时若仍遇到缺项，按预先配置的低阶品质生成并记录原因，避免返回带有空白效果的装备。

地图、战斗和掉落分别使用 `RandomNumberGenerator` 实例，调试时记录种子；Hub 检查点保存长期掉落流，地图和战斗流属于本趟。同版本和相同调用顺序下用于复现；引擎文档明确随机算法属于实现细节，因此跨引擎版本复现需另行验证 [15]。存档恢复已生成物品的实际数值，避免重新抽取。

### 07.3 属性与装备生效

属性修改项保存来源编号、目标属性、适用标签、运算类别和数值。先计算基础值与固定加值，再合并同类百分比加成，最后应用明确声明的独立倍率。概率、冷却下限等边界按属性定义处理。伤害计算继续执行暴击、防御或抗性、护盾和生命扣除。

例：基础伤害 100，固定加值 20，同类加成 30% 与 20%，独立倍率 1.2，结果为 `(100 + 20) × (1 + 0.3 + 0.2) × 1.2 = 216`，随后进入目标防御计算。这里的计算顺序是本项目规则，并非复刻其他游戏。

穿戴时登记该物品的全部属性与触发来源；卸下时按来源编号移除，再刷新属性与技能参数。新增装备效果影响后续攻击，已经提交的伤害请求保持其攻击时快照。读档恢复持久模块和装备，进入 Hub；下一次出发重建最终属性、触发效果及生命/能量和技能计时。

### 07.4 雷霆旋风事件链

旋风在攻击间隔到达时查询范围内敌人的受击区域，按角色编号去重后提交伤害。每个受击目标单独结算暴击。暴击事件满足装备规则时释放一次闪电，闪电按最大跳数、距离、视线和已访问目标集合选择后续目标。闪电命中使存活目标感电；攻击开始时已经感电的目标被击杀时，触发死亡爆炸。

旋风暴击触发闪电的条件只接受玩家直接攻击来源。闪电与爆炸可造成伤害及击杀，爆炸本身不施加感电；爆炸若击杀其他已感电目标，可继续产生死亡爆炸。每个角色只进入死亡流程一次，有限的目标集合决定本次爆破链终点。能量回复分别设定命中与击杀规则，单体战斗也有可用回复来源。

事件最少记录来源角色、目标角色、技能ID、事件ID、根攻击ID、来源类别、伤害类型及暴击结果。触发通过队列顺序处理，避免同步信号层层递归。死亡顺序固定为：标记死亡 → 退出可命中和行动集合 → 提交击杀及掉落 → 播放死亡表现 → 回收节点。

形状查询要显式配置结果数量；官方 `intersect_shape()` 的默认上限是 32 [10]。本项目按支持的活动目标总量及每个目标受击形状数量设置查询容量，并保证单次查询按角色去重；若结果达到容量，在调试中报告截断风险。查询受击区域时启用区域检测并使用对应掩码，世界阻挡另行查询。技能若设计命中上限，需要在说明中明确。视觉表现可以合并，真实伤害与掉落按完整规则结算。

## 08 存档与游戏生命周期

2026-09-12 冻结的 Resource 方案替代原 JSON 与中途恢复设计；当前协议见 [save_system.md](save_system.md)。设置保存为 `user://settings.cfg`；玩家进度为 `user://saves/<角色组 ID>/*.tres`，主索引可重建。

| 保存范围 | 具体内容 |
| --- | --- |
| 完整检查点 | 封装/内容版本、组和检查点 ID、时间、顺序与模块集合 |
| 角色 | 等级、经验、过滤偏好、技能及被动选择 |
| 物品 | 稳定实例 ID、底材/独特内容 ID、历史词条实值、锁定、背包装备仓库归属及容量 |
| 经济 | 金币、材料余额 |
| 据点与进度 | 当前入口/区域选择、难度与奖励进度；后续解锁随模块扩展 |
| 持久随机状态 | 掉落 seed/state 与实例计数；后续据点随机服务独立扩展 |

每个角色五个手动槽、一个自动入口包含最近三个成功版本；仓库当前归角色。仅真实 Hub 保存，探险内请求提示先撤离。正常菜单/退出先结束本趟、回 Hub 结算并成功保存；失败保留会话和旧档，可重试。异常退出回到最后成功检查点，本趟未保存收益丢失。

地图/布局 seed、房间连接与进度、敌人、地面物品、战斗 RNG、技能计时、流血、战吼、药剂与投射物仅留在探险运行态，离场清理；下一次出发重新创建。随机地图任务仍需运行期稳定 ID、连通性与种子复现，当前不恢复中断探险。

持久 Resource 为运行数据源，模块事务发出变化通知；完整快照深拷贝后依次校验、临时写入、读回检查、保留恢复副本、替换及更新索引。候选全部升级/校验/准备成功后整体回到 Hub，失败由玩家选择其他槽，读取本身不自动保存。

已生成词条保留抽取实值，属性根据当前静态定义重建；RNG 使用原生整数，恢复先 seed 后 state。新增模块和字段通过注册协议及明确版本升级扩展。旧 JSON 与旧 expedition 已按本轮决定移除，不提供迁移。暂停仍冻结世界与计时，死亡/撤离保留已拾取长期收益。

## 09 MVP 阶段

MVP（最小可玩版本）包含 M0、M1、M2 三步。M1 验证动作与成型构筑，M2 验证玩家通过掉落走到构筑成型的过程。每一步有可运行交付物，完成验收后再扩展下一步。

| 阶段 | 必须完成的工作 | 可运行交付与验收 |
| --- | --- | --- |
| M0 工程与资产样板 | 建立工程、目录、输入和物理层；引擎与导出模板定版；检查可复用基础服务；接入主题；导入一名角色、一把武器及基础动作；搭建镜头、地面、碰撞和导航样板 | 从仓库重新获取后能导入项目；启动菜单进入场景；玩家正确移动；导出的 Windows 包能在编辑器关闭时启动；记录目标电脑 |
| M1 战斗与成型构筑 | 玩家移动、闪避、普攻、旋风；敌人追击、攻击、受击与死亡；雷霆旋风触发链；生命、能量、暂停；基础音效和命中特效；准备基础与成型两套调试装备 | 同一测试地图切换两套装备可感到明显效率差异；3 分钟连续清怪，触发、死亡和能量循环正确；完成 100 活动敌人的初次压力测试 |
| M2 完整刷宝 MVP | 装备与词条资源、随机掉落、地面标签、拾取与穿脱、属性刷新、背包、锁定、出售、简单仓库、等级成长、整备与再出发、完整存档恢复 | 正常流程清图后获得装备，换装改变战斗；完成出发、清怪、精英、整备与再次出发；回 Hub 保存重启后长期进度与历史词条保持一致，下一趟重建 |

### 09.1 MVP 内容额度

| 内容 | MVP 累计目标 |
| --- | --- |
| 玩家 | 1 名可操作角色，1 套双手近战动作体系 |
| 主动操作 | 普攻、旋风、闪避、恢复药剂 |
| 构筑 | 1 套雷霆旋风；存在基础、部分成型、完整成型三种状态 |

MVP 的前 3 次清图奖励各提供一个尚未领取的核心机制装备选项，同时保留普通随机掉落。奖励领取状态进入存档，确保试玩能接触到完整构筑。进入 Demo 后按内容与经济测试调整保证奖励，明确每件核心装备的目标来源。

### 09.2 MVP 完成标准

① 直接操作能完成移动、闪避、普攻及移动旋风；人物、镜头和鼠标瞄准一致，菜单操作不会穿透到战斗。

② 可以亲眼看到怪物因攻击死亡、装备从死亡位置落地、拾取后进入背包；同一物品在地面、背包、穿戴和读档中的词条数值一致。

③ 装备雷霆机制后，闪电、感电爆炸及回复真实进入结算；卸下对应装备后，后续攻击失去该机制。面对单个精英时仍可继续战斗。

④ 对同一固定怪群、同一等级和同一操作路线，成型预设的清场时间初始目标为基础预设的一半以内；同时记录范围覆盖和操作频率，避免仅靠提高基础伤害冒充机制成型。

⑤ 正常进行 3 趟循环，覆盖升级、替换戒指、背包满、死亡、出售、仓库转移、回城保存退出与下一趟重新出发；期间无崩溃、进度丢失或重复奖励。

⑥ 在 M0 记录的目标机和指定图形设置下完成第 11 节的 MVP 压力场景。当前文档未执行这些验证。

## 11 性能与必要验证

### 11.1 性能目标和测试口径

割草的压力来自角色移动、寻路、动画、连锁查询、粒子和物品标签叠加。下面是项目目标，实际支持数量由 M0 记录的目标电脑测定。

| 场景 | 初始测试负载 | 采集条件 |
| --- | --- | --- |
| MVP 割草压力 | 同时活动的 100 个敌人，镜头内尽量容纳；同时 30 个敌方投射物；100 件地面掉落；完整雷霆旋风 | 固定地图与种子，预热后连续 3 分钟；1080p，约定画质；限帧与垂直同步状态记录在案 |
| Demo 割草压力 | 200 个活动敌人、50 个投射物、150 件掉落标签候选；连锁与爆炸处于正常最大强度 | 同一设备及图形预设，保持 3 分钟可重复遭遇；记录可见与活动数量 |
| 长时间循环 | 连续 30 分钟清图、回城、重开，反复产生与回收怪物、掉落和特效 | 记录内存、节点数、对象数量及切图后能否回落到相近水平 |

目标为稳定 60 帧体验。参考验收预算：95% 帧耗时不超过 20 毫秒，99% 不超过 33.3 毫秒；持续连锁中若出现重复超过 50 毫秒的尖峰，定位对应操作。平均帧率与帧时间分位数一起记录。这些预算在 M0 目标机确定后可调整，发行最低配置需要实际设备验证。

测试记录格式：`构建版本｜CPU｜GPU｜内存｜系统与驱动｜分辨率｜渲染器与画质｜测试场景与种子｜活动/可见对象数｜采样时长｜平均帧率｜P95/P99帧时间｜内存峰值｜现象与结论`。

### 11.2 实现时的性能约定

① 导航网格使用简单碰撞或低复杂度几何生成。敌人移动每个物理步更新，重新设定导航目标按位移阈值或约 0.2～0.5 秒间隔错开处理；沿既有路径行进时仍按导航代理要求更新下一路径点。官方明确建议减少逐帧重算并分散查询 [13][16]。

② 常规敌人采用简化行为状态，远处遭遇按区域激活。局部分离和导航避让分开衡量，MVP 以能通过地图和保持怪群间距为准。实时导航烘焙放在场景准备阶段，D2 优先使用模块预烘焙导航及接缝连接。

③ 目标查找首先复用物理查询。只有实际测量显示它已成为热点，才增加空间分区或其他目标索引；避免在每颗弹体中遍历整张地图的所有敌人。

④ 静态重复地物可使用 `MultiMeshInstance3D` 批量绘制；官方指出 MultiMesh 具有整体可见性判断等限制 [17]。带独立骨骼动画和行为的敌人先使用常规实例，后续依据 CPU、GPU 具体瓶颈选择优化路线。

⑤ 先测创建和释放是否引发尖峰，再为高频特效、弹体或标签增加对象池。池化对象回收时清空命中集合、定时状态、旧目标和回调引用。

⑥ 纯视觉表现允许合并：同一个目标的飘字按短时间窗口合并，远处或被过滤的物品标签减少更新，爆炸音效限制同类并发。真实伤害、触发和掉落保持完整执行。

⑦ 密集战斗主要依靠发光材质、粒子和清晰颜色区分元素；动态阴影灯数量依据实测设定。设置画质选项后分别验证，避免通过关闭关键机制来达到性能指标。

### 11.3 有价值的自动验证

规则测试随系统出现时加入，优先覆盖收益、实例独立性与事件边界。测试入口可先用 Godot 无界面脚本运行；若后续用例数量需要成熟测试框架，再核对当前版本兼容性并接入。

| 测试 | 必须证明的结果 |
| --- | --- |
| 属性计算 | 使用人工可算的小样例验证固定值、同类百分比与独立倍率的顺序；穿脱一件装备能恢复原值 |
| 装备独立性 | 同底材生成两件装备，重铸第一件后第二件及静态定义保持原值 |
| 词条合法性 | 指定标签、等级和品质，结果符合数量、范围、互斥与适用规则 |
| 权重抽取 | 固定种子可复现；使用简单已知分布做抽样检查，按样本量与概率设置统计容差 |
| 重复命中与死亡 | 一个角色有多个受击形状时同次攻击只结算一次；死亡、经验及掉落各发放一次 |
| 触发来源 | 手动攻击暴击可触发闪电；闪电来源无法再次触发同一暴击规则；感电爆炸能完成预期有限传播 |
| 物品转移 | 穿戴替换、背包满格和仓库转移后，每个物品实例仅由一个位置持有 |
| 重铸与材料 | 失败条件下保持原物品与材料；成功时只修改选择的词条位置并扣除一次材料 |
| 存档往返 | Hub 检查点的装备数值、实例归属、经济、成长、入口、奖励进度与下一次掉落对应；多槽回退、升级、坏档重试及离场清理正确 |
| 地图连接 | 生成的入口能到出口和首领，出生点位于可行走区域，导航接缝可通过 |

窗口缩放、手感、音画辨识、暂停、首次引导和发行包启动通过人工试玩验证。新技能效果必须在游戏中观察结算与表现一致。

## 12 Git 与协作规范

① `main` 保持可运行且已验证的状态。功能从 `main` 建立 `feat/whirlwind` 等分支，修复使用 `fix/loot-duplicate`，规范调整使用 `docs/project-plan`。提交信息使用简明中文正文，例如 `feat(loot): 增加精英装备掉落`。每次提交集中表达一个可以说明和验证的改动。

② `.gd`、`.tscn`、`.tres`、`.gdshader` 和文档使用文本方式维护。项目配置、导出预设、导入侧文件及 `.uid` 一并提交；`.godot/` 缓存和 `builds/` 忽略。官方要求把脚本或着色器旁的 `.uid` 纳入版本控制 [18][19]。

③ 大型二进制资产在首次提交前设置 Git LFS（大文件存储），可从 `.blend`、`.glb`、大型 `.png`、`.wav`、`.ogg` 源资产开始；团队机器安装相同工作所需的 LFS。文本资源继续留在普通 Git 历史中 [19]。

④ 同一时间由一名执行者负责同一个 `.tscn`、`.tres` 或 Blender 源工程的修改，开始前说明涉及路径。场景按角色、界面和房间拆分，减少多人同时改总场景。合并完成后重新导入并运行受影响的主入口。

⑤ 重命名或移动资源优先通过 Godot 文件系统面板完成，保留对应 UID；同时检查脚本中的路径及存档内容 ID。文件位置可变，持久内容 ID 维持稳定。

⑥ `AGENTS.md` 写明：开工先读 `README.md`、当前阶段和 `known_trap.md`；优先查固定版本官方能力与已有实现；新增函数与功能添加中文注释；通过场景、信号、资源和组合组件实现职责；交付时说明实际改动、实际验证与遗留。引擎界面操作或导出未经执行时明确标记未验证。

⑦ 运行命令集中维护在 `README.md`，开发文档引用同一入口。已完成阶段使用 Git 标签，如 `v0.1.0-combat`、`v0.2.0-mvp`、`v0.3.0-demo`，包名同时包含平台和版本。

## 13 导入 导出与交付

M0 即建立导出流程。正式预设名暂为 `Windows Desktop`，选择正式场景及其依赖，排除 `debug/`、`tests/` 和测试内容目录。`catalog.tres` 显式引用正式内容，防止资源仅通过字符串访问而漏进导出包。

下列为规划中的命令，当前未执行；`godot` 代表已配置的 Godot 4.7.2 可执行文件，路径相对于仓库根目录。Godot 提供无界面导入和命令行导出能力 [20][21]。

```bash
# 显示实际使用的引擎版本。
godot --version

# 导入项目资源，完成后退出；用于检查导入错误。
godot --headless --path game --import

# 运行正常游戏入口，进行可见的功能验证。
godot --path game

# 输出目录需先存在；导出路径按 Godot 项目目录解析。
godot --headless --path game --export-release "Windows Desktop" ../builds/windows/relic_arpg.exe
```

每次阶段交付包含：Windows 可玩包、操作说明、对应代码版本、内容范围、实际验证结果和已知问题。需要 `.pck` 等伴随文件时一并打包。导出完成后关闭编辑器，从解压目录启动游戏，验证主菜单、进入地图、随机掉落、保存退出和恢复。

Demo 交付额外检查：中文字体与所有模型资源可加载，声音设置和键位设置可保留，正式目录没有调试引用，署名文件覆盖实际使用的第三方资产。对外页面、上传平台和发布文案按后续交付安排处理。
